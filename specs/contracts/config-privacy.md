### 2. 档案（profile）与「一库一进程」

- 档案 = 一套独立的本地库 + 文件目录 + 钥匙。默认两个：`main`（正式服务器）、`test`（测试服务器）
- **测试服务器与正式服务器绝不共用一个档案**：档案目录里记一个标记文件写明是哪种，`use_test_dc` 只从它来；**标记缺失或读不懂就拒绝启动**；`--test-dc` 只是断言它是测试档案
- **号码与档案对得上**：`test` 档案拒绝登录非 `99966` 开头的号，`main` 档案拒绝登录 `99966` 开头的号
- **开发版也能开正式档案**（P4 人定，未取建议）：`cargo build` 出来的程序可以打开正式档案。人已知：会写代码的 AI 能编出任意程序、绕开发送闸（`actions.md` 第一节第 4 小节「威胁边界」）。照旧不变的是 `CLAUDE.md` 第五节「**测试绝不向真实联系人发消息**」。开发、测试时给真实联系人标已读也允许（N3 人定，`.42cog/real.md` 已改）
- **一个档案同时只许一个进程打开**（TDLib 自己会锁库文件，`tdutils/td/utils/port/FileFd.cpp:421,503`）。本项目在起 TDLib **之前**先在档案目录拿一把自己的锁（`atg.lock`，写入进程种类与 pid），拿不到就报 `profile_busy`（`errors.md`），并说清是 CLI 还是 GUI 占着
- **本机接口**（P1 人定：一开始就做 GUI / CLI 共用，接口提前定；实现见 `002_roadmap.md` M0.3、M1.8）：
  - **谁开**：拿到 `atg.lock` 的进程（CLI 或 GUI，下称「执行方」）在 `profiles/<档案>/atg.sock` 监听
  - **谁能连**：只有本用户——档案目录 `0700`、套接字 `0600`，连上后再核对对端进程的用户 id（`getpeereid`），不符即断
  - **怎么转**：后起的 `atg-cli` 拿不到锁时先连套接字；连上就把「子命令 + 参数」作为一行 JSON 发过去，执行方的 `atg-core` 执行，回的是与 CLI 直跑**完全相同**的 JSON 行（`cli.md` 外壳），`watch` 照样持续推事件。连不上才报 `profile_busy`
  - **闸在执行方**：L2 的确认由执行方开凭据，说明里写「来自命令行，可能是 AI」；凭据绝不跨进程（`actions.md` 第一节第 4 小节第 6 条）。L1 按**发起方**的规则（CLI 发来的请求照 CLI：默认不标已读、不发正在输入；AI 推，可推翻）。**直发参数听执行方的**（N1 人定）：执行方不是以直发启动的，就照常弹 Touch ID；CLI 带的 `--unsafe-direct-send` 忽略，并在标准错误说明
  - **秘密不过接口**：登录（验证码、密码）不经本机接口转发，要登录就在执行方那边登
  - 第一阶段 GUI 只当执行方：GUI 启动时档案已被 CLI 占着，报 `profile_busy`（说清是哪个 CLI 进程），请人先关掉它

### 3. 本地库加密（人已定：加密，密钥放钥匙串）

- 用 TDLib 自带的加密：`setTdlibParameters` 的 `database_encryption_key`（`td_api.tl:12185`）
- 钥匙：**32 字节随机数**，首次建档时用系统安全随机源生成，存进钥匙串一条「通用密码」：服务名 `atg.tdlib-db-key`，账户名 = 档案名
- **测试档案也加密**（拍板 8 没有例外；`002_roadmap.md` M1.1 也要求第一阶段加密，这样钥匙串与加密链路在测试里就验证到了）
- **谁能读钥匙**（钥匙串条目的访问控制）：
  - 测试档案与正式档案的钥匙：都认一张本机开发证书（签名稳定，开发期不弹框；P2，**N2 人定：开发证书也管正式档案的钥匙，不弹框**）。人已知：AI 用同一张证书签的任何程序都能拿到正式钥匙
  - 正式发布签名（打包后的安装版）照样在两边的访问名单里
  - 必须有测试：开发证书**以外**的签名（临时签名、别的证书）拿不到任何档案的钥匙（`testing.md` 第一节第 4 小节）
  - 具体用钥匙串的哪种访问控制（传统访问列表还是访问组），开工时实测再定，未核
- 钥匙从钥匙串取出 → 交给 TDLib → 本项目这边尽力清零（已知它会以 JSON 字符串穿过 tdlib-rs 和 TDLib 的内存，那里的副本清不掉）。不进环境变量、不进文件、不进日志、不进命令行参数
- 换钥匙用 `setDatabaseEncryptionKey`（`td_api.tl:12312`），第一阶段不做
- **钥匙丢了怎么办**（钥匙串被清、换机器）：TDLib 报 `Wrong database encryption key`（401，`TdDb.cpp:184`）→ 本项目报 `db_key_invalid`，告诉人「本地缓存打不开，可以清掉缓存重新登录（聊天记录在服务器上，不会丢）」；**清缓存要人确认**，不自动删
- `use_secret_chats=false`（私密聊天第一阶段不做；它的内容只在本机，清缓存会真丢）
- ⚠️ **库加密不覆盖下载的文件**：TDLib 的加密只管数据库；下载下来的图片、语音、文件以**明文**写在 `files/` 目录（`td/telegram/files/FileDownloader.cpp:274-281`：解密后直接写文件）。所以：
  - `profiles/` 下所有目录权限 `0700`（只有本用户能读）
  - 第一阶段**不自动下载**，只在人或命令明确要时下（`file_download`）
  - 用别的应用打开附件（`open_file`）时，复制一份到本应用专用的 `0700` 临时目录再打开，**程序退出时清掉**
  - 下载缓存按大小和时间清理（TDLib 的存储优化接口），默认保留 7 天
  - 剩下的风险（同一用户下的其他程序能读这些明文）P5 人定接受

### 5. 日志：只记形状，不记内容

**白名单**——日志里只许出现：

- 类型名（TDLib 类型、事件名、错误 `code`）
- 数字 id：`chat_id` / `message_id` / `user_id` / `file_id` / `seq` / 请求代次
- 计数、长度、耗时、字节数
- 状态名（`errors.md` 三条线）
- TDLib 错误原文，仅当它「像码」（`errors.md` 第一节第 1 小节）

**黑名单**——绝不出现：消息正文、说明文字、会话标题、人名、用户名、手机号、邮箱、文件名、链接、验证码、密码、钥匙、`api_hash`、代理密码、原始 JSON（收到的和**发出去的请求**都算：发出去的只记类型名）、`serde` 解析错误原文（它会带出出错的值）、panic 信息。

**验收判据**（不是靠自觉；每条都有单测或扫描，`testing.md` 第一节第 4 小节）：

- `model` / 树里**含内容的类型**做类型级脱敏：不派生 `Debug`，统一实现成只打印 `类型 { <redacted> }`（`src/atg-core/src/redact.rs`；本 crate 自己的单元测试里仍派生完整 `Debug`）；**`{:?}` 整个消息、整个 Store 也漏不出内容**，由暗号测试 `src/atg-core/tests/privacy.rs` 测住（每种事件的每个文字字段塞暗号，事件、输入、Store、投影的 `{:?}` 里零出现）。新增带文字字段的类型要登记进 `redact.rs`，并在暗号测试里补上那个字段（拍板 006 甲2）
- `Secret`（密码、验证码、钥匙）用完清零，`Debug` 打印 `<secret>`
- 本项目日志宏只接受白名单类型的字段（编译期拦住）；`String`、`serde_json::Value`、`serde_json::Error` 进不去，解析出错只记「类型名 + 字段路径 + 错误类别」
- tdlib-rs 打原始 JSON 的那一行（`tdlib-rs/src/lib.rs:51`）在补丁里改成只记类型名（拍板 2 自维护补丁；架构方案 R13）
- TDLib 自己的日志：**级别 1 也会漏正文**——`td/telegram/MessageContent.cpp:7696` 的 `LOG(ERROR)` 会把消息改动前后的内容整段打出来。所以启动前（建客户端之前）设 `setLogVerbosityLevel 0`（只记致命错误，`td_api.tl:17622`），输出到第 1 小节的日志文件，单文件上限 10 MB（`logStreamFile`，`td_api.tl:12132`）；只有测试档案可临时调高排查，调高后的日志不许离开本机。原生日志也在「暗号」测试的扫描范围内（`testing.md`）
- 非测试构建装自定义 panic 钩子：丢掉 panic 信息，只留位置和回溯
- 日志保留 7 天，自动轮转

**分享出去时**：日志里的 id 在本机可以留（排查要用），但贴进 issue / 发给别的模型或服务之前，**自动**过打码脚本 `scripts/redact-log`（P3 人定「分享前自动打码」；脚本待写，规则同 `cli.md` 的 `--redact`）（`CLAUDE.md` 铁律 12）。CLI 输出的打码见 `cli.md` 全局选项 `--redact`，定义只在那里。

### 6. 其他隐私规矩

- 截图、录屏：调试时只用假数据（`--fake` / `--fixture`）；对着真实账号截的图不进仓库、不进 PR，非要用先打码
- 无障碍树导出：`--dump-tree` 不带 `--fixture` 就拒绝运行；入库的快照只来自夹具（`testing.md` 第一节第 6 小节）
- **登录**：正式号的登录在 tmux 以外的终端或 GUI 里完成（tmux 窗格的内容能被 `tmux capture-pane` 读走）；验证码、密码都不回显
- CLI 的标准输出带内容，这是它的本职；但 CLI **不写**任何含内容的文件（没有「导出聊天」功能）

## 二、为什么

1. **钥匙进钥匙串、库加密**：人已定（第七节第 8 条）；别人拿到这台 Mac 的文件读不到聊天缓存
2. **自己先拿锁**：TDLib 的锁错误是一句英文、码不稳；先拿自己的锁，能给出「GUI 正开着」这种人听得懂的原因
3. **测试档案与正式档案分开**：两边的账号、消息 id 完全不同，混用会把测试数据写进正式缓存，或把正式会话当成测试会话（发送闸的豁免靠 `use_test_dc` 判断，档案混了豁免就可能误开）
4. **日志靠类型拦，不靠自觉**：「别记内容」写在文档里一定会被某次 `{:?}` 打破；包装类型让它在编译期和 `Debug` 层面就漏不出来（`.42cog/real.md`「隐私：不进日志」）
5. **`device_model` 不写机器名**：这个值会出现在你账号的「活跃会话」列表里，机器名常带真名

**P1. GUI 开着时 AI 想用 CLI，怎么办** —— ✅ 人选：一开始就做共用
一个档案只能一个进程开。AI 友好要求「AI 能只用 CLI 完成任务」，而你用 GUI 时 AI 就用不了 CLI。
- A. 第一阶段就互斥（暂定）：CLI 报 `profile_busy`。最简单
- B. 以后让 GUI 开一个本机接口（仅本用户可连的 Unix 套接字），CLI 发现 GUI 在跑就把请求转给它；发送闸照样在 `atg-core` 里
- 代价：B 多一层进程间协议和权限检查；A 在你用界面时 AI 只能读无障碍树
- 建议：第一阶段 A，GUI 阶段做 B（单开一个 issue）

**P2. 开发期每次重新编译，钥匙串可能都要弹框问「允许 atg-cli 访问吗」** —— ✅ 人选 B；N2 再定：开发证书也管正式档案的钥匙
钥匙串按程序签名认人，每次 `cargo build` 出的程序签名都变，「始终允许」记不住。
- A. 忍着：每次新编译第一次运行点一下允许（会弹窗，算「抢前台」）
- B. 用一个本机自签的开发证书给开发版签名，签名稳定后「始终允许」就记得住
- ~~C. 测试档案不加密~~：撤回（与拍板 8 冲突，codex 评审 004）
- ⚠️ B 的坑：AI 用同一张证书给自己编的程序签名，就能取到钥匙——所以这张证书**只许**用在测试档案的钥匙上，正式档案的钥匙只认正式发布签名（第一节第 3 小节）
- 建议：B（只限测试档案）+ P4

**P3. 日志里要不要留 `chat_id` / `user_id`** —— ✅ 人选 A，分享前自动打码
- A. 留（暂定）：排查「哪个会话出的错」要用；分享前打码
- B. 本机也只记哈希：更保守，排查时要先反查
- 建议：A

**P4. 正式账号（`main` 档案）谁能打开** —— ✅ 人选：开发版也能开
发送闸挡得住走正规接口的 AI，挡不住会写代码的 AI：它能编一个程序，读 `main` 档案的钥匙和 `.env.local` 的 `api_hash`，直接发消息。
- A. 开发版（`cargo build` 出来的）只许开 `test`；`main` 只让仓外、正式签名的安装版打开；落实靠钥匙访问控制只认正式发布签名（第一节第 3 小节）；hook 拦截读正式档案目录和 `security find-generic-password -s atg.tdlib-db-key` 的命令只是辅助
- B. 不限制，靠评审和 hook
- 代价：A 意味着你日常用正式账号要先「安装」一次（多一步打包）；开发和 AI 测试全在测试服务器上
