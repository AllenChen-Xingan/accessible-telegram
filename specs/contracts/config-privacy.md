### 2. 档案（profile）与「一库一进程」

- 档案 = 一套独立的本地库 + 文件目录 + 钥匙。默认两个：`main`（正式服务器）、`test`（测试服务器）
- **测试服务器与正式服务器绝不共用一个档案**：档案目录里记一个标记文件写明是哪种，`use_test_dc` 只从它来；**标记缺失或读不懂就拒绝启动**；`--test-dc` 只是断言它是测试档案
- **号码与档案对得上**：`test` 档案拒绝登录非 `99966` 开头的号，`main` 档案拒绝登录 `99966` 开头的号
- **开发版也能开正式档案**（P4 人定，未取建议）：`cargo build` 出来的程序可以打开正式档案。人已知：会写代码的 AI 能编出任意程序、绕开发送闸（`actions.md` 第一节第 4 小节「威胁边界」）。照旧不变的是 `CLAUDE.md` 第五节「**测试绝不向真实联系人发消息**」。开发、测试时给真实联系人标已读也允许（N3 人定，`.42cog/real.md` 已改）
- **一个档案同时只许一个进程打开**（TDLib 自己会锁库文件，`tdutils/td/utils/port/FileFd.cpp:421,503`）。本项目在起 TDLib **之前**先在档案目录拿一把自己的锁（`atg.lock`，写入进程种类与 pid），拿不到就报 `profile_busy`（`errors.md`），并说清是 CLI 还是 GUI 占着
- **本机接口**（P1 人定：一开始就做 GUI / CLI 共用，接口提前定；实现见 `002_roadmap.md` M0.3、M1.8）：
  - **谁开**：拿到 `atg.lock` 的**常驻**进程（GUI，或 `atg-cli serve`；下称「执行方」）在 `profiles/<档案>/atg.sock` 监听。一次性命令（如 `atg-cli chats`）占着档案的那几秒**不监听**：后来者连不上时再探一次锁，已经空了就改直跑，还占着就报 `profile_busy`，提示稍后重试或常开 `serve`。路径超过 103 字节（macOS `sun_path` 104 字节含结尾的 0）不开接口，报 `internal{what:"socket_path_too_long"}`。上次没正常关留下的 `atg.sock`：执行方拿到锁后删掉重绑（锁在手即无别的活执行方）
  - **谁能连**：只有本用户——档案目录 `0700`（只有本用户能进）、套接字 `0600`（只有本用户能读写），连上后两头都再核对对端进程的用户 id（系统调用 `getpeereid`），不符即断
  - **怎么转**：后起的 `atg-cli`（下称「发起方」）拿不到锁时先连套接字；连上就把「子命令 + 参数」作为一行 JSON 发过去，执行方执行，回的是与 CLI 直跑**相同**的 JSON 行（`cli.md` 外壳；只有执行方当场生成的时间字段不同，见下「协议 v0」），`watch` 照样持续推事件。连不上才报 `profile_busy`。执行方一次处理一个请求，后来的排队等
  - **闸在执行方**：L2 的确认由执行方开凭据，说明里写「来自命令行，可能是 AI」；凭据绝不跨进程（`actions.md` 第一节第 4 小节第 6 条）。L1 按**发起方**的规则（CLI 发来的请求照 CLI：默认不标已读、不发正在输入；AI 推，可推翻）。**直发参数听执行方的**（N1 人定）：执行方不是以直发启动的，就照常弹 Touch ID；CLI 带的 `--unsafe-direct-send` 忽略，并在标准错误说明
  - **秘密不过接口**：登录（验证码、密码）不经本机接口转发；登出会改执行方自己的状态，也不转。`atg-cli serve` 没有登录入口：要登录、登出先停掉它（GUI 在界面里登）。撞上常驻执行方时这类命令报 `profile_busy`，说明写「请先停掉它再跑」
  - **协议 v0**（实现：`src/atg-core/src/ipc.rs`）：
    - **一连一请求**：发起方连上，发**一行** JSON 请求 `{"v":0,"origin":"cli","command":"<子命令>","args":{"format":"json|text","params":{…}}}`，`params` 是发起方按同一份参数定义**解析好**的子命令参数（用法错误在发起方本地报，与直跑一样；执行方按同一个检查入口再查一遍，因为 `params` 绕过了参数解析库）。**影响输出的全局选项**由发起方填进 `params` 的同名字段带过去：现在只有 `history`、`watch` 的 `tz`（读法时区，`--tz`）：只有读消息的读法报钟点；`chats` 的会话项不读时间、`links` 不出读法，所以不用带。以后加命令照这条判断：输出随哪个全局选项变，就把它带过去。请求里的 `v` 是本协议的版本号（v0 即 `0`），**与输出外壳的 `v` 无关**。执行方先看 `v`，对不上回 `internal{what:"ipc_version_mismatch"}`；请求不是 JSON 或形状不对回 `internal{what:"ipc_bad_request"}`（这两种还不知道要哪种格式，一律 JSON 行）。再按 `command` 派发：不认的命令回 `not_implemented`（给 `send` 等以后的命令留位）；登录、登出这组回 `usage`。只连上就断（发起方探一下执行方在不在）不算请求
    - **三种应答帧**，一帧一行：`{"t":"out","line":"…"}`（发起方原样写标准输出）· `{"t":"err","line":"…"}`（原样写标准错误）· 最后恰好一帧 `{"t":"exit","code":N}`（发起方以它退出）
    - **哪些时间字段由执行方生成**：`at`（每行输出时刻）· `result.data.elapsed_ms`（从执行方收到请求起算）· `chats` 的 `first_chat_ms`（执行方进程启动到这个列表第一次有会话；主列表、归档从启动起就在记）。除此之外与直跑逐字节一致（同一段渲染代码；快照测试把这三个字段抹平后比）
    - 连上了但没等到 `exit` 帧就断，或两帧之间 90 秒没动静：发起方补一行 `error(disconnected)`，退出码 4（`errors.md`）
    - **流式订阅**（`watch`；大总管授权 2026-10-26）：请求照旧一行（`command:"watch"`，`params` 里 `chat`、`reveal`、`tz`），帧不加种类、协议不升版本，只是连接一直开着：执行方先回 `status`，之后每个事件一帧 `out`。
      - 执行方不让它占住「一个处理完才接下一个」的请求循环：连接挂进订阅者表（**最多 8 个**，超了回 `usage`：容量满了不算参数错，但第一阶段没有更贴切的码，说明里讲清「已到上限」），之后不论是空闲时喂事件、还是处理别的请求（`chats`、`history`）途中喂，每喂一条都按各订阅者**自己的** `notify` 状态渲染、写给它。写失败、写超时（60 秒），或看到对端已关，就摘掉它（被摘的发起方看到断开，报 `error(disconnected)`、退出码 4）。写是阻塞的：一个读得慢的订阅者最多拖住执行方 60 秒，别的订阅者和请求跟着等（v0 接受）
      - 中途接入：执行方先把流里已到的事件喂完，再看**它自己喂到的**事件里补发是否已结束（见过 `sync_done`、之后连接线没再离开 `ready`）——不看后端此刻的连接线（收线程先改连接线，补发来的事件可能还排在流里没喂）。已结束的，`status` 之后立刻补一行 `sync_done`，之后的都算新消息；还没结束的，等它自己那条（之前补发完过、这次是重连补发的，补发结束时照样汇总它接入后看到的，`cli.md` 第一节第 5 小节「重连汇总」）。`seq` 沿用执行方的：补的这行 `sync_done` 的序号等于执行方最后喂过的那条事件的序号（这个订阅者没见过那条），之后的事件从它加一起连续；起点不是 1
      - `--chat`：执行方替订阅者 `chat_open`，摘掉时 `chat_close`；同一会话几个订阅者按引用计数，只开一次、最后一个走了才关。**`chat_open` 只为订阅，不调 `viewMessages`、不标已读**
      - 结束：发起方 Ctrl+C → 发起方关掉连接、在本地写结尾行 `result`（`reason:"interrupted"`，带本地数的 `events`、`alerts`），退出码 0（同直跑）；执行方停（Ctrl+C / SIGTERM）→ 给每个订阅者写 `result`（`interrupted`）+ `exit 0`；执行方故障 → `error(disconnected)` + `exit 4`
      - 发起方转 `watch` 时**不用** 90 秒帧超时（事件可能很久才来一个），只靠断开认出执行方退出
    - 现在能转的：`chats`、`history`、`links`、`watch`（流式）、`auth state`（只读、不带秘密）。`login`、`logout` 与 `auth` 其余分步不转
  - 第一阶段 GUI 只当执行方：GUI 启动时档案已被 CLI 占着，报 `profile_busy`（说清是哪个 CLI 进程），请人先关掉它

### 3. 本地库加密（人已定：加密，密钥放钥匙串）

- 用 TDLib 自带的加密：`setTdlibParameters` 的 `database_encryption_key`（`td_api.tl:12185`）
- 钥匙：**32 字节随机数**，首次建档时用系统安全随机源生成，存进钥匙串一条「通用密码」：服务名 `atg.tdlib-db-key`，账户名 = 档案名
- **测试档案也加密**（拍板 8 没有例外；`002_roadmap.md` M1.1 也要求第一阶段加密，这样钥匙串与加密链路在测试里就验证到了）
- **谁能读钥匙**（钥匙串条目的访问控制）：
  - **机制**（已定，依据 exp005）：传统登录钥匙串的通用密码条目，有两道关，都在**建条目时**按建它的那个程序记——访问名单认「标识 + 证书」，分区名单认团队号（`teamid:…`；没有团队号的自签名证书只能记程序内容的哈希 `cdhash:…`，重编必弹）。不用访问组（自签名 / 开发身份声明不了受限权限）。术语见 `docs/experiments/exp005-keychain-acl/README.md` 开头「先说几个词」，「静默签名」见同文「安全口径」
  - 测试档案与正式档案的钥匙：都认**本人的 Apple Development 身份**（苹果签发、带团队号）+ 固定标识 `atg.dev`。开发版一律用它签名（`scripts/dev-sign.sh`；在 Apple 芯片本机目标上，cargo 直接运行的程序经 runner 自动签——集成测试里自己再起的二进制不经 runner；身份按 SHA-1 引用，见 `scripts/dev-codesign-id.sh`），重编不弹框（P2；**N2 人定：开发身份也管正式档案的钥匙，不弹框**；身份按 007 改为 Apple Development）
  - **谁能拿到钥匙**（007 A1 人定接受，口径同 P5）：用这个身份、标识 `atg.dev` 签名的任何程序都能不弹框拿到测试与正式钥匙；这个身份的私钥对 codesign 不弹框，所以**同一用户下的任何进程都能自己编一个程序、静默签上名拿到正式钥匙**。注入能过关的开发版程序也能借到它的身份（强化运行时堵这条，#42 缓做）
  - 正式发布签名（打包后的安装版）：按上面的机制，开发版建的条目访问名单里只记开发版的需求（认 Apple Development 证书名），**没有**正式版；所以推断正式版第一次读要人允许一次（exp005 方案对比表乙行的说法带条件「团队号不同才要」，这里按访问名单那道关推得更严）。团队号是否与开发身份相同，未核。留到做正式版时定
  - **迁移过来的两条真条目**（`test`、`main`，2026-10-26 由 atg-dev 时期迁来，人各点一次「始终允许」）：访问名单与分区名单里**旧的 atg-dev 需求、旧 `cdhash:…` 都还在**，只是加了新身份与 `teamid:…`。所以以前人点过允许、还在磁盘上的那几版 atg-dev 程序（及注入它们）照样能读；删掉 atg-dev 证书也去不掉这一层（程序自带签名）。条目还有一个「属主」（有权删条目、改名单的程序），仍是建它的 atg-dev 版：新身份能读、**不能删**（删时报 `-25244` errSecInvalidOwnerEdit）。要删这两条，得用当初建条目的那一版 atg-dev 程序（磁盘上那个文件），否则大概要人在框里输登录密码；这跟删不删 atg-dev 证书无关（程序自带签名；新签的 atg-dev 程序 cdhash 对不上分区名单）——后两句是推断，未测。范围没超出 A1 已接受的「同用户任何进程」。实测出处：`docs/experiments/exp006-keychain-migrate/README.md`
  - 必须有测试：没用这个身份签名的程序（临时签名、自签名证书如 atg-dev、未签名），以及同一身份但标识不是 `atg.dev` 的程序，拿不到**由 Apple Development 版新建的**条目（`testing.md` 第一节第 4 小节；临时签名 / atg-dev 版见 exp005 取证 10 ③，同身份别的标识见 exp006 结论 3）。对迁移过来的真条目不成立（见上一条），对「静默签名」也不成立
- 钥匙从钥匙串取出 → 交给 TDLib → 本项目这边尽力清零（已知它会以 JSON 字符串穿过 tdlib-rs 和 TDLib 的内存，那里的副本清不掉）。不进环境变量、不进文件、不进日志、不进命令行参数
- 换钥匙用 `setDatabaseEncryptionKey`（`td_api.tl:12312`），第一阶段不做
- **钥匙丢了怎么办**（钥匙串被清、换机器）：TDLib 报 `Wrong database encryption key`（401，`TdDb.cpp:184`）→ 本项目报 `db_key_invalid`，告诉人「本地缓存打不开，可以清掉缓存重新登录（聊天记录在服务器上，不会丢）」；**清缓存要人确认**，不自动删
- `use_secret_chats=false`（私密聊天第一阶段不做；它的内容只在本机，清缓存会真丢）
- ⚠️ **库加密不覆盖下载的文件**：TDLib 的加密只管数据库；下载下来的图片、语音、文件以**明文**写在 `files/` 目录（`td/telegram/files/FileDownloader.cpp:274-281`：解密后直接写文件）。所以：
  - `profiles/` 下所有目录权限 `0700`（只有本用户能读）
  - 第一阶段**不自动下载**，只在人或命令明确要时下（`file_download`）
  - 用别的应用打开附件（`open_file`）时，复制一份到本应用专用的 `0700` 临时目录再打开，**程序退出时清掉**
  - 下载缓存按大小和时间清理（TDLib 的存储优化接口），默认保留 7 天
  - 剩下的风险（同一用户下的其他程序能读这些明文）P5 人定接受

### 5. 日志：只记形状，不记内容

**白名单**——日志里只许出现：

- 类型名（TDLib 类型、事件名、错误 `code`）
- 数字 id：`chat_id` / `message_id` / `user_id` / `file_id` / `seq` / 请求代次
- 计数、长度、耗时、字节数
- 状态名（`errors.md` 三条线）
- TDLib 错误原文，仅当它「像码」（`errors.md` 第一节第 1 小节）

**黑名单**——绝不出现：消息正文、说明文字、会话标题、人名、用户名、手机号、邮箱、文件名、链接、验证码、密码、钥匙、`api_hash`、代理密码、原始 JSON（收到的和**发出去的请求**都算：发出去的只记类型名）、`serde` 解析错误原文（它会带出出错的值）、panic 信息。

**验收判据**（不是靠自觉；每条都有单测或扫描，`testing.md` 第一节第 4 小节）：

- `model` / 树里**含内容的类型**做类型级脱敏：不派生 `Debug`，统一实现成只打印 `类型 { <redacted> }`（`src/atg-core/src/redact.rs`；本 crate 自己的单元测试里仍派生完整 `Debug`）；**`{:?}` 整个消息、整个 Store 也漏不出内容**，由暗号测试 `src/atg-core/tests/privacy.rs` 测住（每种事件的每个文字字段塞暗号，事件、输入、Store、投影的 `{:?}` 里零出现）。新增带文字字段的类型要登记进 `redact.rs`，并在暗号测试里补上那个字段（拍板 006 甲2）
- `Secret`（密码、验证码、钥匙）用完清零，`Debug` 打印 `<secret>`
- 本项目日志宏只接受白名单类型的字段（编译期拦住）；`String`、`serde_json::Value`、`serde_json::Error` 进不去，解析出错只记「类型名 + 字段路径 + 错误类别」
- tdlib-rs 打原始 JSON 的那一行（`tdlib-rs/src/lib.rs:51`）在补丁里改成只记类型名（拍板 2 自维护补丁；架构方案 R13）
- TDLib 自己的日志：**级别 1 也会漏正文**——`td/telegram/MessageContent.cpp:7696` 的 `LOG(ERROR)` 会把消息改动前后的内容整段打出来。所以启动前（建客户端之前）设 `setLogVerbosityLevel 0`（只记致命错误，`td_api.tl:17622`），输出到第 1 小节的日志文件，单文件上限 10 MB（`logStreamFile`，`td_api.tl:12132`）；只有测试档案可临时调高排查，调高后的日志不许离开本机。原生日志也在「暗号」测试的扫描范围内（`testing.md`）
- 非测试构建装自定义 panic 钩子：丢掉 panic 信息，只留位置和回溯
- 日志保留 7 天，自动轮转

**分享出去时**：日志里的 id 在本机可以留（排查要用），但贴进 issue / 发给别的模型或服务之前，**自动**过打码脚本 `scripts/redact-log`（P3 人定「分享前自动打码」；脚本待写，规则同 `cli.md` 的 `--redact`）（`CLAUDE.md` 铁律 12）。CLI 输出的打码见 `cli.md` 全局选项 `--redact`，定义只在那里。

### 6. 其他隐私规矩

- 截图、录屏：调试时只用假数据（`--fake` / `--fixture`）；对着真实账号截的图不进仓库、不进 PR，非要用先打码
- 无障碍树导出：`--dump-tree` 不带 `--fixture` 就拒绝运行；入库的快照只来自夹具（`testing.md` 第一节第 6 小节）
- **登录**：正式号的登录在 tmux 以外的终端或 GUI 里完成（tmux 窗格的内容能被 `tmux capture-pane` 读走）；验证码、密码都不回显
- CLI 的标准输出带内容，这是它的本职；但 CLI **不写**任何含内容的文件（没有「导出聊天」功能）

## 二、为什么

1. **钥匙进钥匙串、库加密**：人已定（第七节第 8 条）；别人拿到这台 Mac 的文件读不到聊天缓存
2. **自己先拿锁**：TDLib 的锁错误是一句英文、码不稳；先拿自己的锁，能给出「GUI 正开着」这种人听得懂的原因
3. **测试档案与正式档案分开**：两边的账号、消息 id 完全不同，混用会把测试数据写进正式缓存，或把正式会话当成测试会话（发送闸的豁免靠 `use_test_dc` 判断，档案混了豁免就可能误开）
4. **日志靠类型拦，不靠自觉**：「别记内容」写在文档里一定会被某次 `{:?}` 打破；包装类型让它在编译期和 `Debug` 层面就漏不出来（`.42cog/real.md`「隐私：不进日志」）
5. **`device_model` 不写机器名**：这个值会出现在你账号的「活跃会话」列表里，机器名常带真名
