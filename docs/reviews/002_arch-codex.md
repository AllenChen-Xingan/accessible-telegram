## 发现与处理

行号指评审时的方案版本。

- **P1｜:67 `edit_date` 保证不了合并与到达顺序无关**：`updateMessageContent` 不带时间，`updateMessageEdited` 不带内容。
  - 核实：属实（`td_api.tl:11217,11230`）
  - 处理：一.3 第 6 条改成：收线程给更新编序号；历史请求记下「发出时的序号 + 请求代次」，作为版本边界；发出后被更新碰过的消息以 store 为准；按字段合并（内容只认内容更新，编辑时间只认编辑更新）；撤回留墓碑；交错顺序有单测
- **P1｜:118 只用消息 id，没带会话**：TDLib 的消息 id 只在所属会话内唯一。
  - 核实：属实（`td_api.tl:3551`）
  - 处理：store、墓碑、焦点锚点、元素 id 一律用 `(会话 id, 消息 id)`；历史应答校验会话和代次；列表元素 id 带上会话 id
- **P1｜:65 「把积压一次取完」不让出主线程**：一次 `notify()` 也不等于一帧一批。
  - 核实：属实（是设计缺陷，无需源码）
  - 处理：每批设条数和时间上限，处理完 `notify` 一次并让出主线程；积压过大时按会话合并，当前会话丢掉窗口、按版本边界重新拉历史
- **P1｜:98 收线程崩溃后，请求终止没有可执行的机制**：静态的 `OBSERVER` 不释放一次性信道，`send_request` 会一直等。
  - 核实：属实（`tdlib-rs/src/lib.rs:23,65-68`；`observer.rs` 的 sender 存在全局表里）
  - 处理：加监督和故障广播；每个请求同时等应答和故障信号；故障后拒绝新请求；关闭设超时；补丁去掉 `receive()` 里会崩的 `unwrap`
- **P1｜:188 发送确认只覆盖 CLI，没覆盖 GUI 和 computer use**：违反 `intent.md:16`「无论走哪条路都须人确认」。
  - 核实：属实
  - 处理：确认移到 `atg-core` 的发送入口，要一张绑定「目标 + 内容摘要」的确认凭据，CLI 和 GUI 各自开凭据的方式写明。「AI 能不能经界面替人按确认」和「测试时发收藏夹免不免确认」两件要人定，列为第七节第 9、10 条
- **P1｜:189 依赖自己的日志会泄露内容**：tdlib-rs 解析不了更新时，把整条原始 JSON 打进日志。
  - 核实：属实（`tdlib-rs/src/lib.rs:51`）
  - 处理：接真实账号前，补丁删掉原始内容；TDLib 日志级别调低、日志文件放仓外；本项目日志不记内容；加泄露测试。另记风险 R13
- **P2｜:241 `only_local` 用错了地方**：`getChats` / `loadChats` 没有这个参数。
  - 核实：属实（`td_api.tl:12502,12507,12758`）
  - 处理：第一刀第 5 块改用 `loadChats` 加会话更新维护排序；离线首屏另行验证，记风险 R14
